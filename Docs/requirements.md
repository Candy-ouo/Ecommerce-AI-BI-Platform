## 一、项目概述

### 1.1 项目名称

**基于大数据的电商用户行为分析与AI智能BI平台**

### 1.2 项目背景

电商是国内数字经济第一大产业，2025 年全国网上零售额超 15 万亿元。阿里巴巴 2014 年双 11 移动端成交占比达 42.6%，超过 240 亿元——移动电商的"随时随地"特性使得用户行为数据爆炸式增长。

然而，**数据量的增长并不等于数据价值的释放**。多数电商企业的现状是：用户行为日志躺在服务器里，运营决策凭经验拍板，活动效果无法量化评估。传统 BI 系统（如 FineBI、Superset）虽然能提供基础报表，但存在三个具有明确学术理论支撑的根本性缺陷——不是技术不够快，而是**交互模式本身有瓶颈**。

---

#### 痛点一："看数难"——信息过载时代的注意力稀缺

**理论依据：Herbert Simon 注意力经济学（1971）**

> *"A wealth of information creates a poverty of attention."* —— 信息越丰富，注意力越稀缺。

在电商运营场景中，**不是没有数据，而是数据太多**。一个运营人员面对几十张报表、上百个指标，不知道该看哪个——注意力被数据洪流淹没。传统 BI 的解决思路是"做更多报表、加更多筛选器"，但这恰恰**加剧了信息过载**。

Alvin Toffler 在《Future Shock》（1970）中预言：当信息量超过人类的处理能力时，决策质量不升反降。这解释了为什么很多企业上了 BI 系统后运营效率反而没有明显提升——**报表越多，真正被看的越少**。

**本项目的解法：Pull + Push 双模驱动，从"人找数"到"数找人"**

| 模式 | 机制 | 解决场景 |
|------|------|----------|
| **Pull（拉取）** | NL2SQL 自然语言查询：用户主动提问 → LLM 生成 SQL → 执行 → 返回结果 + 图表 | 用户知道自己要什么，一步直达 |
| 🔥 **Push（推送）** | AI 智能晨报：每日 8:00 自动分析昨日指标 → 环比 7 天前 → 识别异常 → LLM 生成报告 → 钉钉/邮件推送 | 用户**不知道**该关注什么时，系统主动告知 |

---

#### 痛点二："分析难"——DIKW 金字塔的"最后一公里"

**理论依据：Russell Ackoff DIKW 金字塔（1989）**

| 层级 | 含义 | 示例 |
|------|------|------|
| **Data（数据）** | 原始符号记录 | `user_id=100234, behavior_type=4` |
| **Information（信息）** | 经过结构化处理的事实 | "昨日购买转化率 4.2%" |
| **Knowledge（知识）** | 对因果关系的解释 | "转化率下降是因为数码品类遭遇竞品促销" |
| **Wisdom（智慧）** | 可指导行动的决策建议 | "建议数码品类限时降价 10%，预计挽回 3% 转化率" |

**传统 BI 卡在 Information 层**——报表告诉你"转化率 4.2%"，但不告诉你"为什么不是 4.7%"，更不告诉你"怎么办"。这就是 **"最后一公里"问题**。

John Sweller 的**认知负荷理论（1988）** 进一步解释：人类工作记忆容量有限（约 4±1 个信息块），运营人员面对多维交叉分析时认知负荷早已超载。

**本项目的解法：AI 承担 Information → Knowledge → Wisdom 的跃迁**

| DIKW 跃迁 | 系统如何实现 | 对应模块 |
|-----------|-------------|----------|
| Data → Information | 数仓 ODS→DWD→DWS→ADS 四层聚合 | 数据仓库模块 |
| Information → Knowledge | LLM 读取 ADS 指标 → 自动发现异常 → 输出因果分析 | AI 数据洞察 + AI 智能晨报 |
| Knowledge → Wisdom | Agent 综合多维度分析 → 生成可执行的运营建议 | Agent 自助分析 |

---

#### 痛点三："推荐难"——算法黑箱与信任鸿沟

**理论依据：Pasquale "黑箱社会" + DARPA XAI + Davis TAM**

法学家 Frank Pasquale 在《The Black Box Society》（2015）中指出：**当算法决策不透明时，用户会本能地不信任它**。电商推荐系统正是典型黑箱——用户看到"猜你喜欢"但不知道为什么推荐这些。这不只是体验问题，更是**商业问题**：运营无法判断推荐逻辑是否合理，不敢把结果直接用于推送策略。

美国 DARPA 2016 年启动的 **XAI（Explainable AI，可解释人工智能）** 项目明确提出：AI 系统必须能够解释自己的决策逻辑。

Fred Davis 的**技术接受模型（TAM，1989）** 指出用户接受技术的两个关键因素——感知有用性和感知易用性。推荐黑盒在这两个维度上天然打折。

**本项目的解法：可解释推荐**

> 协同过滤给出 Top N 推荐 → LLM 为每条结果生成可读理由：
> *"推荐商品 A（相似度 0.92）：您最近浏览了同类商品 B 和 C，相似用户中 78% 最终购买了 A。"*

---

#### 痛点与解法总结

| 痛点 | 理论根源 | 传统 BI 的局限 | 本项目解法 |
|------|---------|---------------|-----------|
| **看数难** | Simon 注意力经济学 / Toffler 信息过载 | 人找数 | NL2SQL（Pull）+ AI 智能晨报（Push）→ 数找人 |
| **分析难** | Ackoff DIKW 金字塔 / Sweller 认知负荷 | 卡在 Information 层 | AI 洞察 + Agent：自动完成 Information→Knowledge→Wisdom |
| **推荐难** | Pasquale 黑箱社会 / DARPA XAI / Davis TAM | 黑盒无解释 | LLM 推荐理由，可解释、可追溯 |

### 1.3 项目定位

本项目基于**阿里天池Mobile Recommendation真实电商用户行为数据集**（约1225万条行为记录、48万商品信息），构建一个集**大数据批处理、机器学习建模、AI大模型交互**于一体的电商用户行为分析与智能BI平台。

核心价值主张：**自然语言驱动数据分析，AI Agent编排复杂任务，机器学习赋能预测与推荐。**

### 2.5 行为类型映射

| 编码 | 行为类型 | 业务解读               | 数量          | 占比   |
|------|----------|------------------------|---------------|--------|
| 1    | 浏览(pv) | 用户查看商品详情页      | 11,550,581    | 94.2%  |
| 2    | 收藏(fav) | 用户收藏该商品          | 242,556       | 2.0%   |
| 3    | 加购(cart) | 用户将商品加入购物车    | 343,564       | 2.8%   |
| 4    | 购买(buy) | 用户实际下单完成支付    | 120,205       | 1.0%   |

### 2.6 数据集特点与约束

**特点（优势）：**
- 两张表构成：行为表 + 商品信息表，可通过item_id关联，构建完整的商品维度
- 31天行为数据，时间跨度足够支持周级别趋势分析和用户留存分析
- 1225万行规模适中，单机Spark即可高效处理
- 行为类型分布真实（浏览94.2% / 加购2.8% / 收藏2.0% / 购买1.0%），符合电商业务特征
- 商品信息表提供了991个类目的维度支撑，可用于Item-CF协同过滤和类目分析
- user_geohash和item_geohash约32%-36%有值，可视需要做地理位置分析

**约束（限制）：**
- 用户仅10,000人，量级偏小，用户维度的统计分析结论需谨慎外推
- 无商品价格/金额字段，无法计算GMV、客单价等金额指标
- 无用户画像属性（性别/年龄/地域），需从行为中推导用户特征
- 商品信息表存在大量重复（48万行中仅31万去重商品），清洗时需去重处理
- 商品表与行为表的CategoryID不一致（行为表8,916个 vs 商品表991个），以行为表为准
- 时间粒度为小时级（非秒级），无法做分钟级实时分析

### 2.7 开发数据策略

| 环境     | 数据量       | 用途                                        |
|----------|-------------|---------------------------------------------|
| 开发调试  | 10,000条    | E从用户行为表随机抽取，与商品表join后分发      |
| 全量运行  | 1225万条（行为表）+ 48万条（商品表） | A在Hive/Spark上执行清洗与ETL                  |

## 三、业务场景与目标用户

| S4       | 转化漏斗分析   | 全链路行为漏斗（浏览 → 收藏 → 加购 → 购买），定位各环节转化率与流失情况                     |
| S5       | 复购预测       | 基于用户历史行为特征，使用XGBoost模型预测用户复购概率，识别高潜力用户                   |
| S6       | 个性化推荐     | 基于Item-CF协同过滤算法，为用户推荐可能感兴趣的商品                                   |
| S7       | 实时大屏监控   | 展示核心经营指标（订单量、UV、PV、转化率），支持定时刷新与趋势展示                     |
| S8       | AI智能问答     | 自然语言提问→NL2SQL转SQL→执行→返回结果+图表+自然语言解读                             |
| S9       | AI Agent分析  | 用户给定高层级分析任务，AI Agent自动规划→调用多工具→汇总生成分析报告                    |

### 5.2 核心指标定义

| 指标类别   | 指标名称           | 计算口径                                               | 存储层 |
|------------|--------------------|--------------------------------------------------------|--------|
| 流量指标   | DAU（日活跃用户数） | 当日有浏览行为的UserID去重计数                          | ADS    |
| 流量指标   | PV（页面浏览）      | 当日behavior_type='浏览'的记录数                        | ADS    |
| 互动指标   | 加购用户数          | 当日behavior_type='加购'的UserID去重计数                | DWS    |
| 互动指标   | 收藏用户数          | 当日behavior_type='收藏'的UserID去重计数                | DWS    |
| 交易指标   | 订单量              | 当日behavior_type='购买'的记录数                         | ADS    |
| 交易指标   | 购买用户数          | 当日购买行为的UserID去重计数                              | ADS    |
| 交易指标   | 全站购买转化率      | 购买用户数 / DAU                                       | ADS    |
| 商品指标   | 商品PV热度          | 某商品浏览行为数 / 全站浏览行为数                         | DWS    |
| 商品指标   | 商品购买转化率      | 某商品购买行为数 / 某商品浏览行为数                      | DWS    |
| 用户指标   | 人均PV              | 总PV / DAU                                            | ADS    |
| 用户指标   | 人均购买次数        | 总购买行为数 / 购买用户数                                 | ADS    |
| RFM指标    | R值                 | 用户最近一次行为距统计截止日期的天数                      | ADS    |
| RFM指标    | F值                 | 用户在统计周期内购买行为的次数                             | ADS    |
| RFM指标    | M值（广度）         | 用户购买行为涉及的去重ItemID数（替代金额维度）              | ADS    |

## 七、API接口规范（概要）

以下接口由C实现，作为C→D、B→C的团队接口契约：

| 接口                          | 方法 | 说明                   | 返回示例                                          |
|-------------------------------|------|------------------------|---------------------------------------------------|
| `/api/kpi/cards`              | GET  | 核心KPI指标卡          | `{"dau":12345,"dau_change":-0.03,"orders":8900,"conversion_rate":0.12,"avg_pv":8.5}` |
| `/api/trend/active?days=7`    | GET  | 近N日活跃趋势          | `{"dates":["07-14",...],"dau":[12000,...],"pv":[96000,...]}` |
| `/api/top/items?limit=10`     | GET  | 商品热度TopN排行       | `{"items":[{"item_id":xxx,"pv":8900,"buy":320},...]}` |
| `/api/funnel`                 | GET  | 全站转化漏斗           | `{"pv":100000,"fav":35000,"cart":20000,"buy":8000}` |
| `/api/rfm/dist`               | GET  | RFM 8类用户占比分布    | `{"labels":["重要价值",...],"counts":[1200,...]}` |
| `/api/recommend?user_id=123`  | GET  | 个性化推荐列表         | `{"items":[{"item_id":xxx,"score":0.92},...]}` |
| `/api/chat`                   | POST | AI对话（SSE流式）      | SSE事件流，支持text/chart/done三种事件类型          |
| `/api/report/latest`          | GET  | 🔥 最新AI晨报          | `{"date":"2014-12-18","content":"今日DAU...","anomalies":["数码品类转化率下降12%"]}` |
| `/api/report/history?days=7`  | GET  | 🔥 历史晨报列表        | `[{"date":"...","content":"...","anomalies":[...]}, ...]` |

**SSE事件格式规范**：

```
data: {"type":"text","content":"好的，我来帮你查询..."}
data: {"type":"text","content":"上周购买量最高的5个类目是：..."}
data: {"type":"chart","chartType":"bar","data":{...}}
data: {"type":"done"}
```

**SSE 晨报推送事件格式**（大屏实时接收）：

```
data: {"type":"report","content":"今日DAU 12,345（环比+3%），转化率4.2%...","anomalies":["数码品类销量下降12%"]}
```

## 八、非功能性需求

### 8.1 性能需求

| 指标             | 目标值                                             |
|------------------|---------------------------------------------------|
| NL2SQL查询响应   | ≤ 10秒（含LLM推理 + SQL执行 + 解读）                |
| 预计算报表响应   | ≤ 2秒（查询ADS层预聚合结果）                         |
| 🔥 AI晨报生成    | ≤ 30秒（ADS指标读取 + LLM生成 + 推送完成）            |
| 大屏数据刷新间隔 | 30秒                                              |
| 全量ETL完成时间  | ≤ 20分钟（1225万行全量导入+清洗+DWD/DWS/ADS分层计算） |
| 并发用户数       | 支持10并发用户（答辩演示场景）                        |

### 8.2 易用性需求

- 纯HTML/CSS/JS前端，浏览器打开即用，无需Node.js/npm构建
- 大屏为暗色主题的单页面Dashboard，信息密度高、层级清晰
- AI对话面板呈现在大屏右侧，支持文字+图表混合输出
- 所有ID类字段在展示时附带类目标签等可读性辅助信息

### 8.3 可扩展性需求

- 新增分析指标时优先通过配置ADS层新表实现，尽量不改动DWD/DWS层
- AI模块`llm_client.py`统一封装，支持切换不同大模型API
- Agent工具函数通过HTTP调用后端API，新增工具只需在`tools.py`中增加函数

### 8.4 数据安全需求

- 数据集本身已脱敏（UserID/ItemID/CategoryID均为序列化整数），无需额外脱敏
- API接口需基础鉴权
- 关键ETL任务操作需记录日志
